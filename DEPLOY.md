# Прод: развёртывание и обновление

Прод — отдельная Linux-машина. На ней не собирают образы и не держат
исходники: она забирает готовый образ, собранный CI, и запускает его.

**Правило, которое важнее всех остальных: с ноутбука разработчика в прод-базу
не ходят.** Ни `migrate`, ни `dbshell`, ни «только посмотреть». Локальная
разработка ведётся на своём стеке, у прода своя жизнь.

## Что где

| | Где | Чем разворачивается |
|---|---|---|
| Прод | отдельная Linux-машина | `docker-compose.yml` + `compose.prod.yml`, образ из ghcr |
| Разработка | ноутбук каждого | `docker-compose.yml` + `compose.dev.yml`, сборка локально |
| Образы | `ghcr.io/lokehoke/my-spotify` | собирает `release.yml` на каждый коммит в `main` |

Секреты прода живут в `/opt/my-spotify/.env` **на самой прод-машине** — не в
репозитории и не в переменных GitHub. Рабочую папку раннер пересоздаёт, поэтому
деплой копирует этот файл к себе перед запуском.

## Подготовка машины

1. **Docker и compose:** по инструкции дистрибутива, плюс
   `systemctl enable --now docker`, иначе после перезагрузки ничего не
   поднимется.

2. **Запретить засыпание.** Ноутбук с закрытой крышкой уходит в suspend и
   уносит прод с собой:

   ```
   # /etc/systemd/logind.conf
   HandleLidSwitch=ignore
   HandleLidSwitchExternalPower=ignore
   ```

   плюс `systemctl mask sleep.target suspend.target hibernate.target`.

3. **Окружение:** скопировать `.env.prod.example` в `/opt/my-spotify/.env` и
   заполнить. Все значения — свои, не совпадающие с локальными.

4. **Self-hosted раннер.** Машина стоит дома за NAT, и снаружи до неё не
   достучаться. Раннер решает это тем, что сам опрашивает GitHub: проброс
   портов не нужен. Ставится из Settings → Actions → Runners, метки —
   `self-hosted` и `prod` (их ждёт `deploy` в `release.yml`). Запускать
   сервисом (`./svc.sh install && ./svc.sh start`), иначе он не переживёт
   перезагрузку.

5. **Наружу** — Cloudflare Tunnel либо Tailscale. Приложение слушает только
   `127.0.0.1:8000`, так что порт на роутере пробрасывать не нужно и не стоит.
   Туннель должен ставить `X-Forwarded-Proto` — на него смотрит
   `SECURE_PROXY_SSL_HEADER` из `config/settings/prod.py`.

## Первый запуск

```bash
sudo mkdir -p /opt/my-spotify && sudo cp .env.prod.example /opt/my-spotify/.env
```

Дальше — заполнить `.env` и запустить деплой вручную: вкладка Actions →
Release → Run workflow.

## Обычное обновление

- **по тегу:** `git tag v0.1.0 && git push --tags` — собирается образ и
  разворачивается;
- **вручную:** Actions → Release → Run workflow;
- **просто коммит в `main`** образ соберёт, но разворачивать не будет.

Деплой делает ровно три вещи: `pull`, `migrate` отдельным шагом, `up -d`.
Миграции вынесены из команды контейнера намеренно — иначе несколько воркеров
начнут применять их одновременно. После старта деплой ждёт `/readyz` и падает,
если приложение не ответило за минуту.

## Откат

Образы тегируются по коммиту, поэтому откат — это разворачивание прошлого тега:

```bash
docker compose -f docker-compose.yml -f compose.prod.yml pull
```

с `APP_IMAGE=ghcr.io/lokehoke/my-spotify:sha-<коммит>` в `/opt/my-spotify/.env`,
затем `up -d`. **Миграции назад не откатываются** — если релиз их содержал,
сначала думаем, потом откатываем.

## Бэкапы

Прод — единственное место с настоящими данными, и он стоит на ноутбуке.
Как минимум: `pg_dump` по cron на другой физический диск и копия бакетов MinIO.
Бэкап, который лежит на той же машине, бэкапом не является.

## Чего эта схема не умеет

ARCHITECTURE.md §8.1 описывает прод на нескольких машинах с managed PostgreSQL
и прямо называет базу единственным компонентом, потеря которого фатальна.
Ноутбук дома — не оно: нет ни репликации, ни PITR, ни второго узла. Это
осознанная стадия «пока пользователей нет». Как только появятся чужие данные,
базу надо уводить в managed — `DATABASE_URL` читается из окружения, так что
переезд стоит одной строки.
